En este capítulo, describiremos en detalle la guía operativa del proyecto, detallando los pasos necesarios para que cualquier usuario o investigador pueda replicar el entorno de trabajo, ejecutar el \textit{pipeline} de datos y reproducir los análisis descritos en capítulos anteriores.

	\item \textbf{Uso de modelos y evaluación de resultados:} Guía para la ejecución de los algoritmos y la extracción de conocimiento a partir de los resultados.
\end{itemize}

De este modo, intentaremos garantizar la transparencia del código y la total trazabilidad del ciclo de vida del dato, desde su ingesta hasta el modelado de Inteligencia Artificial. Al final, también estableceremos una comparativa de que nubes o entornos es mejor utilizar en cada caso, según lo estudiado en este trabajo. \section{Ingesta y descarga de datos} 
\label{sec:Manual_Ingesta}

El proceso de ingesta requiere Python 3.12 o superior y poder instalar las dependencias de \texttt{requirements.txt} (preferiblemente en un entorno virtual). Todo el comportamiento del \textit{pipeline} se controla desde el fichero, \texttt{config.py}, que centraliza las rutas de las capas de almacenamiento, las direcciones web de los conjuntos en los portales de datos, los años a descargar, los filtros de formato, las reglas de limpieza y los parámetros de los análisis. 
Incorporar un conjunto de datos nuevo consiste, por tanto, en añadir una entrada en los diccionarios correspondientes, y modificar, si es necesario, la lógica de los procesos.

La ruta base del proyecto es la definida en la variable \texttt{TFM\_BASE}, si esta no existe, se utiliza el directorio local del proyecto

\begin{lstlisting}[language=bash, caption={Preparación del entorno y ejecución de la ingesta}]
	python -m venv .venv
	source .venv/bin/activate          # o en Windows: .venv\Scripts\Activate.ps1
	pip install -r requirements.txt
	
	python 01_descarga.py --dry-run    # comprueba que los datos existen, sin descargar
	python 01_descarga.py              # descarga completa
\end{lstlisting}

El proceso es idempotente, es decir, puede relanzarse sin volver a descargar lo ya presente, y registra los metadatos de procedencia de cada fichero en \texttt{\_metadatos.csv}. Debido a la protección anti-automatización de los portales también incorpora pausas entre descargas y reintentos, por lo que una ingesta completa puede durar varios minutos.

\subsection{Despliegue en Local} 
\label{subsec:Manual_Despliegue_Local}

La ejecución local no requiere infraestructura adicional más allá del entorno descrito en la Sección \ref{sec:Manual_Ingesta}. Los procesos se ejecutan secuencialmente y cada uno utiliza la salida del anterior como entrada. Aunque para este trabajo se ha utilizado un entorno local, se podrian usar herramientas como notebooks de google o los entornos de hugginface para ejecutar estos comandos sin la necesidad de un hardware personal.

\begin{lstlisting}[language=bash, caption={Ejecución completa del pipeline en local}]
	cd code/files
	python 01_descarga.py              # bronze
	python 02_limpieza.py              # silver
	python 03_analisis_isla_calor.py   # resultados
\end{lstlisting}

Esta línea base local cumple con el propósito de validar los datos de los trabajos originales en un entorno controlado antes de introducir la variable de la nube, y de servir de referencia frente a la que comparar las implementaciones en cada proveedor.

\subsubsection{Configuración del entorno y autenticación}

Aunque desde \textbf{AWS CloudShell} se gestionan las credenciales de acceso con el usuario que hemos registrado, es posible configurar credenciales de acceso externas para otros usuarios, para que los diferentes servicios en la nube los utilicen, o para ejecutar los comandos desde local. El proyecto se realizó siguiendo las mejores prácticas, mediante el modelo de control de acceso basado en roles y grupos (RBAC), y aunque se podrían establecer permisos mas estrictos, y este modelo tiene mas sentido para manejar un numero mayor de usuarios,  se realizó para futuras extensiones del proyecto y para la utilizacion de herramientas y roles de servicio. 

Lo primero para trabajar con la nube, es seleccionar la region que mas convenga al proyecto, que en este caso es la región \texttt{eu-west-1} (Irlanda), ya que es la que mayor número de servicios ofrece dentro de la Unión Europea. Con esto, en la propia \textbf{AWS CloudShell}, se puede obtener el código del proyecto, publicado bajo licencia abierta, de la siguiente manera:

\begin{lstlisting}[language=bash, caption={Obtención del código fuente del proyecto}]
	cd ~
	git clone https://github.com/crismo04/TFM-cloud-soliutions-to-public-data.git
	cd TFM-cloud-soliutions-to-public-data/code/files
	pip install -r requirements.txt --quiet
\end{lstlisting}

También conviene tener creadas las variables de entorno que vamos a utilizar en el proyecto. Ademas, al trabajar con la terminal, se  conserva el directorio personal entre sesiones, pero no las variables de entorno definida. Para no tener que volver a crearlas cada sesión, se pueden almacenar en un fichero que se carga al comenzar cada sesión:

\begin{lstlisting}[language=bash, caption={Persistencia de las variables del proyecto}]
	cat > ~/tfm-env.sh << 'EOF'
	export BUCKET="tfm-ucm-datos-publicos"
	export REGION="eu-west-1"
	export CUENTA=$(aws sts get-caller-identity --query Account --output text)
	export TFM_BASE="s3://$BUCKET"
	EOF
	
	source ~/tfm-env.sh
\end{lstlisting}


\subsubsection{Infraestructura de Almacenamiento en Amazon S3}

El almacenamiento en la nube se fundamenta en un \textit{bucket} de Amazon S3 denominado \texttt{tfm-ucm-datos-publicos}. Su estructura replica exactamente la jerarquía de directorios local, y de otras nubes: (\texttt{data/bronze/}, \texttt{data/silver/}, \texttt{resultados/} (como capa Gold) y \texttt{scripts/}). Permitiendo así que el código de Python migre entre ambos entornos cambiando únicamente el prefijo de ruta de archivo. Se aplican también, mediante los siguientes comandos, bloqueo total de acceso público, versionado de objetos y etiquetado para el seguimiento de costes.

\begin{lstlisting}[language=bash, caption={Creación y configuración de seguridad del contenedor en S3}]
	# Creacion del bucket
	aws s3api create-bucket --bucket "$BUCKET" --region "$REGION" \
	--create-bucket-configuration LocationConstraint="$REGION"
	
	# Bloqueo de acceso publico
	aws s3api put-public-access-block --bucket "$BUCKET" \
	--public-access-block-configuration \
	"BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"
	
	# Versionado y etiquetado
	aws s3api put-bucket-versioning --bucket "$BUCKET" \
	--versioning-configuration Status=Enabled
	
	aws s3api put-bucket-tagging --bucket "$BUCKET" \
	--tagging 'TagSet=[{Key=proyecto,Value=tfm}]'
\end{lstlisting}

Una vez creado el contenedor, se puede ver en el apartado de S3 instantáneamente y ya podemos proceder a cargar los procesos de ingesta directamente sobre el almacenamiento creado. Con esto, validamos la portabilidad, ya que el mismo proceso que se ejecutó en local escribe ahora en S3 sin ninguna modificación de su lógica, gracias a la abstracción del sistema de ficheros con \texttt{fsspec} descrita en la Sección \ref{sec:Metodos_ingesta}.

\begin{lstlisting}[language=bash, caption={Carga de los procesos e ingesta directa sobre S3}]
	# Carga de los scripts del pipeline
	aws s3 cp . "s3://$BUCKET/scripts/" --recursive --exclude "*" --include "*.py"
	
	# Ingesta escribiendo directamente en la capa bronze del bucket
	python 01_descarga.py --destino "s3://$BUCKET/data/bronze/"
	
	# Verificacion del contenido cargado
	aws s3 ls "s3://$BUCKET/data/bronze/" --recursive --summarize
	
\end{lstlisting}

\subsubsection{Orquestación y Procesamiento ETL con AWS Glue}

Para el procesamiento de datos en la nube se ha optado por ``AWS Glue Python Shell'' en lugar de entornos distribuidos basados en ``Apache Spark''. Dado que los conjuntos de datos tratados en este proyecto ocupan 272 MB en su capa bronce, el uso de \textit{Spark} implicaría una sobrecarga innecesaria y un coste mínimo de 2 DPU (Data Processing Units), mientras que \textit{Python Shell} permite ejecutar con un mínimo de 0,0625 DPU ($\approx 0,03$\$/hora), incluyendo librerías como \texttt{pandas}, \texttt{numpy} y \texttt{scikit-learn} ya instaladas. 

A diferencia de la ejecución en terminal del apartado anterior, Glue se ejecuta desde su propio apartado en AWS, puede programarse o encadenarse con otros, y es mas fácil de automatizar, a parte de que nos permite explorar las posibilidades de la nube. El primer paso es crear la cuenta de servicio, siguiendo los principios que hemos comentado al principio de este capítulo:

\begin{lstlisting}[language=bash, caption={Creación del rol de servicio de Glue}]
	# Politica de confianza: solo el servicio Glue puede asumir este rol
	cat > trust.json << 'EOF'
	{"Version":"2012-10-17","Statement":[{"Effect":"Allow", "Principal":{"Service":"glue.amazonaws.com"},"Action":"sts:AssumeRole"}]}
	EOF
	
	aws iam create-role --role-name AWSGlueServiceRole-tfm \
	--assume-role-policy-document file://trust.json \
	--tags Key=proyecto,Value=tfm
	
	aws iam attach-role-policy --role-name AWSGlueServiceRole-tfm \
	--policy-arn arn:aws:iam::aws:policy/service-role/AWSGlueServiceRole
	
	aws iam attach-role-policy --role-name AWSGlueServiceRole-tfm \
	--policy-arn arn:aws:iam::aws:policy/AmazonS3FullAccess
\end{lstlisting}

Para utilizar \textit{Python Shell} es necesario empaquetar los módulos propios que hemos creado, como el fichero de configuración. Durante el desarrollo se ha comprobado que un fichero comprimido en formato \texttt{zip} se descarga correctamente pero no llega a importarse, mientras que un paquete en formato \textit{wheel} sí se instala como cualquier otra dependencia, por lo que lo hemos hecho de la siguiente manera:

\begin{lstlisting}[language=bash, caption={Empaquetado del módulo de configuración}]
	rm -rf /tmp/pkg && mkdir -p /tmp/pkg
	cp ~/TFM-cloud-soliutions-to-public-data/code/files/config.py /tmp/pkg/
	
	cat > /tmp/pkg/setup.py << 'EOF'
	from setuptools import setup
	setup(name="tfmconfig", version="1.0.0", py_modules=["config"])
	EOF
	
	cd /tmp/pkg && pip wheel . -w dist --no-deps --quiet
	aws s3 cp dist/tfmconfig-1.0.0-py3-none-any.whl "s3://$BUCKET/scripts/"
	
	cd ~/TFM-cloud-soliutions-to-public-data/code/files
	aws s3 cp . "s3://$BUCKET/scripts/" --recursive --exclude "*" --include "*.py"
	
\end{lstlisting}

Si posteriormente se modifica el fichero de configuración, es necesario regenerar el paquete e \textbf{incrementar su número de versión}, ya que en caso contrario el gestor de dependencias reutilizaría la copia previamente instalada.

Con el rol y los procesos disponibles solo falta crear la función, para esto, fijaremos un tiempo máximo de ejecución, una capacidad máxima y desactivaremos los reintentos automáticos como medida de control de costes. También añadiremos etiquetas para poder desglosar el gasto. 
La definición se declara en JSON en lugar de como argumentos en línea, para mayor visibilidad de rutas y evitar el escapado de comillas, ya que ambas han dado problemas en la ejecución:

\begin{lstlisting}[language=bash, caption={Definición y despliegue del trabajo de limpieza (02) en AWS Glue}]
	source ~/tfm-env.sh
	# Aborta si la variable esta vacia, evitando rutas del tipo s3:///
	: "${BUCKET:?Variable BUCKET vacia, ejecutar source ~/tfm-env.sh}"
	
	cat > job-limpieza.json << EOF
	{
		"Name": "tfm-02-limpieza",
		"Role": "AWSGlueServiceRole-tfm",
		"Command": {"Name": "pythonshell", "PythonVersion": "3.9",
			"ScriptLocation": "s3://$BUCKET/scripts/02_limpieza.py"},
		"DefaultArguments": {
			"--extra-py-files": "s3://$BUCKET/scripts/tfmconfig-1.0.0-py3-none-any.whl",
			"--additional-python-modules": "s3fs",
			"--TFM_BASE": "s3://$BUCKET"},
		"MaxCapacity": 0.0625,
		"Timeout": 15,
		"MaxRetries": 0,
		"Tags": {"proyecto": "tfm", "fase": "limpieza"}
	}
	EOF
	
	cat job-limpieza.json    # comprobacion de las rutas resueltas
	aws glue create-job --cli-input-json file://job-limpieza.json
\end{lstlisting}

Esto de nuevo, es sencillo por tener los .py configurados, pero para añadir mas datos solo seria necesario incluir su entrada en \texttt{config.py}, actualizar el repositorio con las especificidades de estos, y volver a sincronizar los procesos con el almacenamiento mediante el ciclo descrito en este trabajo. 
Con esto ya podemos lanzar la ejecución y ver el resultado:

\begin{lstlisting}[language=bash, caption={Ejecución, seguimiento y verificación del resultado}]
	RUN=$(aws glue start-job-run --job-name tfm-02-limpieza \
	--query JobRunId --output text)
	
	aws glue get-job-run --job-name tfm-02-limpieza --run-id "$RUN" \
	--query "JobRun.[JobRunState,ExecutionTime,ErrorMessage]" --output text
	
	# Registro de la ejecucion
	aws logs tail /aws-glue/python-jobs/output --since 10m
	
	# La capa silver debe aparecer en el bucket al finalizar
	aws s3 ls "s3://$BUCKET/data/silver/" --recursive --summarize
	
\end{lstlisting}

\subsubsection{Modelos de ML y resultados con Amazon SageMaker} 
\label{sec:Manual_Modelos_sagemaker}

Para generar esta última capa de análisis en AWS, vamos a volver a cambiar de tecnología.
Mientras que la etapa \textit{Silver} se completó mediante \textit{AWS Glue}, la etapa de análisis tiene otros requerimientos: ejecución de algoritmos, cálculo de siluetas, volumen elevado de figuras, librerías de tratamiento geoespacial, etc. Todo esto se beneficia de una ejecución interactiva durante la interpretación de los resultados. 

Por ello, para generar esta capa final, vamos a emplear \textbf{Amazon SageMaker}. Específicamente, el servicio de \textit{Spaces} dentro de un dominio, que proporciona entornos de \textit{Jupyter Notebooks}. Lo primero es la creación de este dominio, que se realiza desde la consola web \footnote{SageMaker disponible en: \url{https://eu-west-1.console.aws.amazon.com/datazone/home?region=eu-west-1\#/}}, con la configuración de inicio rápido en la región \texttt{eu-west-1}. 

AWS aprovisionará automáticamente las redes virtuales (VPC) y el almacenamiento (EFS) con el dominio. Una vez creado, el espacio aprovisiona automáticamente el entorno de desarrollo \textbf{JupyterLab} mediante IDE, ademas de muchas otras funciones, que se pueden ver en la figura \ref*{figura_AWS_Consola_sagemaker}.

Desde la terminal integrada en el cuaderno, se descarga el repositorio, se instalan librerías y se sincronizan \textit{Silver} y datos descargados en el paso de ingesta. Finalmente, se publican los resultados en el almacenamiento masivo S3:

\begin{lstlisting}[language=bash, caption={Ejecución del análisis en el entorno de SageMaker}]
	# Dentro del terminal de JupyterLab en SageMaker
	git clone https://github.com/crismo04/TFM-cloud-soliutions-to-public-data.git
	cd TFM-cloud-soliutions-to-public-data/code/files

	# Ejecucion del analisis y generacion de figuras
	python 03_analisis_isla_calor.py
	
	# Publicacion de los resultados en el bucket
	aws s3 sync resultados/ s3://tfm-ucm-datos-publicos/resultados/
\end{lstlisting}

De nuevo, la ejecución no requiere modificación del código fuente para ejecutar en este entorno. Emplear \texttt{JupyterLab} para el trabajo analítico, facilita visualizar gráficos y tablas directamente en el entorno, y publicar después en el almacenamiento de objetos una vez estudiada la salida.

De nuevo, la ejecución no requiere modificación del código fuente. El entorno de cuadernos dispone de sistema de ficheros local, por lo que los gráficos y las tablas se generan directamente en disco y se publican después en el almacenamiento de objetos, evitando las adaptaciones que habrían sido necesarias en el servicio de procesamiento desatendido, como reescribir la salida de cada gráfico hacia flujos de bytes o resolver las dependencias nativas de las librerías geoespaciales.


Conviene advertir que, desde una perspectiva de control de costes, los espacios de trabajo facturan por tiempo de aprovisionamiento mientras permanecen encendidos, con independencia de que se esté utilizando el cuaderno o no. Conviene detenerlos manualmente desde la administración del dominio al finalizar cada sesión para interrumpir la facturación.

\section{Uso de modelos y resultados} 
\label{sec:Manual_Modelos}

Cada ejecución del análisis genera un directorio por cada año con los diagramas del codo, dendrogramas, gráficos de dispersión de correlaciones y tablas de grupos.
Al finalizar también produce tres resúmenes: el coeficiente de silueta por año y aproximación, la correlación entre superficie arbórea y temperatura por año, y un diagnóstico de cobertura de días válidos por estación.

El parámetro \texttt{MODO\_REPLICA} determina si se reproducen las condiciones del trabajo original o se aplican los criterios metodológicos propios definidos en la sección \ref*{sec:Metodos_analisis}, y los resultados de cada modo se almacenan en directorios separados. La salida completa queda registrada en \texttt{ejecucion.log} para facilitar la trazabilidad de las ejecuciones y los parámetros elegidos.
